# 数据与展示约定

## 求职条件与匹配约定

目标岗位、公司、城市、薪资任选即可；简历、经历可选。不同维度条件交集，同维度多个选项通常取并集；“优先”只影响排序，“必须”作为硬限制。多城市明示包含目标城市可纳入。

薪资按用户最新口径解析上下限、币种和周期。范围可按交集筛选，但“最低”需下限满足；用户明确“上限大于35k”则上限严格 >35k。只标下限且已大于门槛时可纳入，不编造上限。面议/缺失不能当成满足明确限制；不默认12薪或把股权算成保证现金。必要歧义简短澄清。

内推与人脉按公司和方向关联，不强制与某条岗位的城市、薪资、团队完全一致，但不能声称这些线索满足全部硬条件。内推范围与公司关联分别记录。岗位无结果不阻塞公司线索交付。

## 优先输入结构

渲染命令：`python scripts/render_job_list.py response.json output.html`，只用 Python 标准库。`response.json` 是本次允许展示的有限结果，不含凭据、全量库或完整采集记录。

```json
{
  "title": "白领求职捷径 · 上海算法",
  "context": "上海 · 算法 · 按本次约定的薪资条件",
  "companies": [
    {
      "company": "已核验公司名称",
      "company_id": "可选的已核验主体标识",
      "referral_posts": [],
      "has_company_people": false,
      "jobs": [],
      "referral_status": "本次未核验到内推供给帖",
            "jobs_status": "本次未核验到符合条件的关联岗位"
    }
  ],
  "skills": [
    {
      "role_name": "算法",
      "sample_based": true,
      "sample_size": 0,
      "items": [],
      "status": "尚无足够的已核验 JD 样本，暂不展示技能排名。"
    }
  ]
}
```

这是结构占位示例，不是真实公司或岗位。单次最多20家公司、50个岗位。未限定公司时，通常从约30–40家相关候选中争取核验并整理15–20家有内推线索的公司；不足时如实交付，可附带有匹配岗位的公司，大厂与有相关业务的明星公司、行业头部或成长公司均可纳入；关联岗位通常附带最多20个。公司线索优先，实际不足如实返回，不用数量目标迫使填充无证据内容。候选、已查、已核验、无结果、受限的覆盖记录另存审核数据；候选数量不等于交付数量，仅有岗位的公司不计入已核验内推/人脉公司数。用户明确的公司范围与数量优先。

### 内推帖子 referral_posts

- `title`：详情页原标题或正文开头，不生成营销标题。
- `author`、`content_excerpt`：页面显示名、连续原文节选；原帖可省略节选并用 `content_verified: true` 标记已核验。
- `url`、`published_at`、`observed_at`：真实链接、原页明确时间及本次观察时间。观察时间不代替发布时间。
- `scope`：公司、团队、岗位、城市、校招/社招的真实范围。
- `availability`：当前内推意愿和有效性，仅作内部核验记录，未确认时如实记录；不渲染到用户清单，也不显示替代提示文案。
- 审核记录另存 `referral_evidence`、`company_name`、`association_level` 和主体关系证据。正文无内推意愿证据的普通招聘帖子不放入此字段。

### 公司人脉入口

按 `company` 构造“去获取该公司人脉”按钮，无需读取找人结果或个人主页，不接收个人主页作为按钮地址。已有核验的官方搜索找人链接格式为：

`https://maimai.cn/web/search_center?type=contact&query={编码后的公司名称}&highlight=true`

`query` 必须完整使用 UTF-8 百分号编码（含空格、`&`、`#`），不拼接原始公司名，不把公司名当作个人 ID。该页面是公司关键词的人脉搜索，具体结果和筛选能力以站内为准，不声称全部结果都是当前员工。公司名缺失时不生成虚构关键词。

人脉区域只显示上述入口，不显示姓名、职位、个人简介、头像、人数或个人主页链接；不把这些信息嵌入 HTML、隐藏属性或对外响应 JSON。默认不读取个人主页、不查询具体人员，人员状态记为“未查询”。构造链接无需登录，但用户点击进入站内后仍可能被要求登录；不承诺站内人脉结果或投递也可免登录。

`has_company_people` 保留为历史数据兼容字段，新调用默认省略或置 `false`，不为设置该值而查询个人主页；它是可选的公司级实际核验状态：只有独立证据确认本次确有相关员工/HR时才设为 `true`；缺省或 `false` 不证明全站无人。导航始终不构成人脉命中。旧版 `employees` 仅为内部证据兼容字段，渲染时不输出内容；新对外结果应移除该字段，以可选公司级状态替代。历史证据只表示当次已核验关系，不虚构好友关系或内推承诺；默认流程不新增具体人员核验。

### 关联岗位 jobs

每项展示字段含 `title`、`company`、`salary`、`city`、`education`、`experience`、`detail_url`，`note` 可选。JD 核验原文单独保留在内部 `detail_sections:[{heading,text}]`，节选在 heading 标明；对外 JSON 不需要 JD 全文或发布者个人资料。

新审核记录可包括真实岗位标识、实际列表或原帖来源、`observed_at`、`discovery_method`、`match_reasons`、`skill_evidence` 和实际访问状态，但不嵌入 HTML；不采集发布者个人主页、个人职位列表或履历。按 ejid 去重，字段冲突不改写原文。JD 原文仅作核验和统计，不在 HTML 内折叠展示；岗位卡片直接提供“查看岗位详情”，进入已核验的脉脉官网岗位页，不在每个岗位里重复技能词或公司线索。

新岗位审核记录可保存 `source_referral_url`、`association_level` 及真实来源证据，按实际来源填写“同帖”或“同公司”；不新增 `source_person_url` 或“同人”主页核验链路。历史记录中已有的人员字段仅作兼容，不作为本次默认采集要求；没有证据不补全链条。前端保留帖子的 `scope` 与岗位的 `note`，不渲染 `employees` 中的个人资料及链接、人员 `reason` 和帖子 `availability`；不把这两项补充说明转移到其他展示字段。仍不把“同公司关联岗位”写成“此人承诺内推的岗位”。

兼容旧版顶层 `jobs` 数据：渲染器按有证据的 company_id 或完全相同的公司名聚合，并合并重复帖子/人员；不推断集团别名。旧 `jobs[].skills` 会去重后移到最后，旧 `professional_keywords` 不再在岗位内展示。新 `companies` 与旧顶层 `jobs` 不同时传入，以免重复和归属混淆。请新调用使用 `companies`。

## 技能统计规则

- 只统计本次已读取、属于目标职能和筛选范围的 JD；岗位按 ejid 去重，明显重复的招聘需求另作说明，必要时保守合并统计并报告分母。
- 从职责和任职要求识别专业知识、工具、技术、方法或资格，保留原文证据；排除软技能、学历、年限、薪资、福利、岗位名本身及公司介绍中的无关词。
- 必备和优先条件都可计为 JD 提及，但不把优先项称作普遍硬门槛。排除否定要求，例如“不要求 Python”。
- 合并真正同义词，机器学习与深度学习等不同概念不合并。每岗位每词只计1次；按涉及岗位数降序，同数稳定排序，保存命中 ejid 和证据。
- `skills` 为统计对象数组：`role_name`、`sample_based:true`、`scope`、`snapshot_at`、`sample_size`、`items:[{keyword,job_count}]`。样本不足时 `items:[]` 并填写 `status`。
- “算法”等宽工种包含各细分方向时统一一份榜、同一个分母；仅互不相关工种分榜。最多10项，不凑词；只有一份 JD 时不生成排名。
- 标为“本次样本”，不称全站或全市场；占比为词项涉及岗位数 / 实际样本岗位数，不是竞争力或录用率。
- 只在全部公司卡片之后显示，不置顶，不放在每个岗位下方。没有岗位不影响内推和人脉清单。

## 展示与入口

顺序：白领求职捷径标题与条件 → 公司卡片（内推帖子、公司人脉、关联岗位）→ 技能 TOP10 → Skill 简介与下载入口。

页尾“前往下载skill”按钮固定使用 `https://github.com/yaoyiyi0828/Hana-AI-1`，点击在新标签页打开仓库首页。使用普通 HTTPS 链接，设置 `target="_blank" rel="noopener noreferrer"`，不带 `download` 属性；仓库用于后续同地址更新分发。

主线索区域采用两块醒目的浅色底，内推在前、公司找人入口在后。桌面并列，手机纵向。关联岗位为紧凑摘要区，JD 保存在核验数据中，完整描述进入脉脉官网阅读。“查看内推帖”回原帖，“去获取该公司人脉”回该公司的搜索找人页，“查看岗位详情”直接打开具体官网岗位页，保留原始真实链接，不统一改为首页。按钮不会自动发消息、加好友、申请内推或投递。

页头不显示数据日期和数量；正常岗位不显示来源/采集时间脚注、“匹配依据”或下载二维码；仅无结果兜底点击后弹出二维码。帖子时间和范围、技能样本日期保留用于判断。当前任职不代表愿意内推，旧帖不代表当前有效，岗位页可访问不代表招聘仍开放。

无岗位时在公司卡片显示准确查询状态，仍保留内推和公司找人入口；无内推时也不隐藏公司找人入口。人员查询状态留在审核记录，导航按钮不意味着已核验到具体员工。

当一家公司没有实际内推、人员或岗位结果（`referral_posts`、旧版内部 `employees`、`jobs` 均为空，且 `has_company_people` 不为 `true`）时，在该公司卡片的关联岗位区域之后显示醒目的主按钮：“前往脉脉，搜索“HR”，进入大厂急招HR专场”，使用蓝底白字、较大字号和整行布局，手机端可自动换行。点击后在同页弹出 `assets/maimai-download-qr.png` 原图，不自动导航。图片通过 data URL 嵌入生成的 HTML，二维码等比缩放、不裁切或重绘；多家空公司复用一个弹窗，支持关闭按钮、Esc 和关闭后焦点返回。用户扫码后打开脉脉，搜索“HR”进入专场，不宣称自动直达活动。任一项有实际结果时不显示此兜底；自动生成的公司找人按钮不算实际人员结果。用户明确指定的公司即使三项为空也保留公司名称与卡片，不能为了凑覆盖量加入其他空候选公司。未指定公司且整体为空时，在全局空状态提供同一主按钮，不虚构公司。此入口只用于无结果兜底，正常“去获取该公司人脉”按钮仍指向该公司的找人搜索页。各模块仍分别保留“未查询”“受限”“本次未核验到”等真实状态；链接只提供下一步入口，不证明全站没有相关内容。不能用搜索摘要伪装详情，不凭名称近似跨主体归并。

## 工作边界

按 [浏览器适配规则](browser-adaptation.md) 选择执行路径：优先宿主可操作的内置浏览器；内置能力不足时，使用用户在宿主中配置的浏览器自动化技能、浏览器 MCP、扩展或 CDP 工具。浏览器品牌、用户配置及打开方式遵循宿主设置；配置为系统默认浏览器时才采用实际默认浏览器。不能把只有打开链接的能力当成可控制页面或已具备登录态读取能力。

用户在选定的可控浏览器会话中登录脉脉，检索和详情核验复用该会话；未登录或过期时才展示并保留官方登录页，由用户完成并确认。不同浏览器、配置、手机 App 或其他 Agent 的登录不默认互通。优先后台运行；完全隐藏、后台标签或可见执行按宿主能力及用户设置处理，用户明确要求完全隐藏但无法满足时保留进度并暂停相应查询，不宣称后台标签、最小化或不抢焦点等于完全隐藏。

审核记录可保存执行模式、打开/控制/读取能力、实际可见性、登录核验状态及受限原因，不保存 Cookie、连接密钥、会话标识或其他凭据；未配置工具、登录过期、验证码及页面受限均不写成没有结果，不以匿名请求代替登录查询。最终交付清单，不打开个人主页，不自动联系或投递。本包不含 NBI、未开放岗位 API、全量数据库、浏览器连接器、定时服务或归因埋点。各宿主的能力需实际验证，不因导入成功或修改指令就宣称已实现跨平台适配或后台服务。未验证的原生 App 唤起只描述为打开脉脉页面。

如果以后另建私有推荐服务，全量库与凭据留在服务端，仅返回授权的有限结果；这不是当前使用前提。
